# Lyrica–Archisynapse Integration Contract

## Royalty Receipt Loop v1 · Empire-1 Ecosystem

**Status:** Draft for implementation
**Products:** Lyrica 3 (producer) → Archisynapse v2 (consumer/executor)
**Boundary:** `POST /api/v1/events` on the Archisynapse gateway
**Operating rule honored:** WE EVOLVE. NEVER DELETE. Both schemas carry `schema_version`; consumers MUST tolerate unknown fields; breaking changes require a new major version, never mutation of v1.

---

## 1. Principles

1. **Lyrica creates obligations. Archisynapse moves money.** Lyrica never writes to the ledger; Archisynapse never decides what a creative act is worth.
2. **At-least-once delivery, exactly-once effect.** Lyrica may send an event any number of times; Archisynapse guarantees at most one financial effect per `idempotency_key`.
3. **Every hop shares one `correlation_id`.** It must appear in Lyrica's outbox, the gateway log, the transaction record, the journal entry metadata, and the receipt.
4. **The receipt is the only source of truth for Lyrica's Earnings screen.** Lyrica renders creator-facing status exclusively from receipt fields, never from its own guesses.

## 2. Transport & Security

| Concern | Specification |
|---|---|
| Endpoint | `POST https://{archisynapse-gateway}/api/v1/events` |
| Auth (tenant) | `Authorization: Bearer <tenant API key>` — tenant identity resolved by SLA113-issued key |
| Signature | `X-Empire1-Signature: ed25519=<base64(sig)>` over the exact raw request body bytes |
| Key identity | `X-Empire1-Key-Id: <key id>` — public keys registered per tenant via SLA113 |
| Correlation | `X-Correlation-Id: <ULID>` — generated by Lyrica at obligation creation, immutable thereafter |
| Idempotency | `Idempotency-Key: <ULID>` — unique per obligation, stable across retries |
| Replay bound | `occurred_at` in body must be within ±5 minutes of gateway clock, else `422 stale_event` (retry with same idempotency key after clock fix is safe) |
| Content type | `application/json; charset=utf-8` |

Signature verification failures are **recorded** (a rejection row with correlation_id, key_id, reason) but create **no** financial objects.

## 3. Royalty Event Schema (`royalty.obligation.created`, v1)

```json
{

  "event_type": "royalty.obligation.created",
  "occurred_at": "2026-07-20T18:00:00Z",
  "correlation_id": "01J8ZC4K7Q2M9XN3P5R7T9V1AA",
  "idempotency_key": "01J8ZC4K7Q2M9XN3P5R7T9V1BB",
  "tenant_id": "lyrica",
  "track": {
    "track_id": "trk_9f3a2b1c",
    "dna_tag": "dna_v2_7c1e...",
    "soulprint_hash": "sp_sha256_4b09...",
    "vics_proof": {
      "proof_id": "vics_01H...",
      "issued_at": "2026-07-01T12:00:00Z",
      "chain_ref": "vics://empire1/lyrica/trk_9f3a2b1c"
    }
  },
  "creator": {
    "creator_id": "cre_a1b2c3",
    "identity_ref": "sla113://identity/cre_a1b2c3"
  },
  "splits": [
    { "owner_id": "cre_a1b2c3", "bps": 6000 },
    { "owner_id": "cre_d4e5f6", "bps": 4000 }
  ],
  "trigger": {
    "kind": "remix",
    "source_ref": "lyrica://remix/rmx_7788",
    "actor_id": "usr_listener_42"
  },
  "amount": { "currency": "USD", "value": "1.2500" }
}
```

**Validation rules:** `splits[].bps` MUST sum to exactly 10000. `amount.value` is a fixed-point string with exactly 4 decimal places (matches Archisynapse BigInt ledger units). `trigger.kind` ∈ {`play`, `remix`, `license`}. Unknown top-level fields are ignored, never rejected.

## 4. Money Math (normative)

All arithmetic in integer ten-thousandths (units = value × 10000), matching the v1 monolith ledger convention.

**`amount.value` is the creator royalty pool, in full. Archisynapse deducts nothing from it.** There is no platform fee in this loop — Lyrica canon is a flat $1.25 per-remix payout to the creator(s), full stop. Empire's separate 70/30 platform-revenue-share policy governs a *different* pricing contract entirely (e.g. subscription or licensing revenue) and MUST NOT be applied to this event unless a distinct, founder-approved contract explicitly states that `amount.value` is gross platform revenue rather than a creator payout. Absent that, treat this section as authoritative: 100% of the pool is owed to creators.

1. **Splits:** apply `bps` directly to the pool (`amount.value`), floor each share to the cent, then distribute any leftover cents by **largest fractional remainder**; ties broken by larger bps, then lexicographic `owner_id`. Deterministic — the same event always yields the same cents. (For splits that divide evenly — e.g. 60/40 of $1.2500 — there is no remainder to distribute; the algorithm still applies, it just has nothing to do.)
   `$1.2500 at 60/40 → 0.7500 / 0.5000 exactly, no rounding needed.`
2. **Invariant:** `sum(payouts) == pool`, always, enforced by a balanced-journal check before commit.
3. **Amounts payload:** `gross` and `net` are both the pool value (no fee separates them in this loop); `platform_fee` stays present in the schema for forward compatibility but is always `"0.0000"` here — see §6.

## 5. Decision Outcomes & Ledger Effects

A `royalty.obligation.created` event on its own proves nothing was collected — it is a *promise* to pay, not evidence of cash in hand. It therefore posts as an **expense/payable**, not a clearing-account movement. `royalty_clearing` (an asset-side processor account) is only correct when the event carries a reference to an actual captured payment funding the royalty — not modeled in the v1 schema; when it is, ledger effects below switch from `royalty_expense` to `royalty_clearing` for the debit leg.

| Decision | Receipt `status` | Ledger effect |
|---|---|---|
| Allow | `processing` → `paid` | DR `royalty_expense` 1.25 / CR `creator_payable:{owner}` 0.75 + 0.50 |
| Hold | `held` | DR `royalty_expense` 1.25 / CR `royalty_held_liability` 1.25 (obligation recorded, no payable created, no money moves) |
| Block | `blocked` | No financial entries. Decision + reasons persisted with correlation_id |
| Release (of held) | `processing` → `paid` | Reclass: DR `royalty_held_liability` / CR payables, same event_id, no new obligation |
| Reversal | `reversed` | Linked reversing entries (existing v2 reversal semantics); post-reversal trial balance delta = 0 |

**Hold release:** `POST /api/v1/events/{event_id}/release` — authorized via SLA113 policy role only. Idempotent: the first authorized call pays; every subsequent call (any number of times) returns `200` with the *same stored receipt* — never a second payment, and never a `409` for a call that's simply repeating a released event. `409 invalid_state` is reserved for releasing an event that was never held (blocked, allowed, or unknown) in the first place.
**Reversal:** Lyrica emits `royalty.obligation.reversed` with `reverses_event_id`, its own `idempotency_key`, same `correlation_id`. Idempotent the same way: retrying a reversal returns `200` with the original reversal receipt, never a second reversing entry.

## 6. Unified Receipt Schema (v1)

Returned synchronously (v1) as the response body; identical object retrievable at `GET /api/v1/receipts/{receipt_id}`.

```json
{
  "schema_version": "1.0",
  "receipt_id": "rcp_01J8ZC...",
  "status": "paid",
  "status_reasons": [],
  "event_id": "01J8ZC4K7Q2M9XN3P5R7T9V1WX",
  "correlation_id": "01J8ZC4K7Q2M9XN3P5R7T9V1AA",
  "transaction_id": "txn_5f7b2571",
  "ledger_transaction_id": "ldg_txn_8d1287",
  "amounts": {
    "currency": "USD",
    "gross": "1.2500",
    "platform_fee": "0.0000",
    "net": "1.2500"
  },
  "payouts": [
    { "owner_id": "cre_a1b2c3", "amount": "0.7500", "state": "paid" },
    { "owner_id": "cre_d4e5f6", "amount": "0.5000", "state": "paid" }
  ],
  "decision": {
    "policy": "allow",
    "risk_score": 0.12,
    "checks": ["ownership_verified", "dna_match", "vics_valid"]
  },
  "issued_at": "2026-07-20T18:00:01Z",
  "signature": { "alg": "ed25519", "key_id": "arch-rcpt-k1", "value": "base64..." }
}
```

`status` ∈ {`processing`, `paid`, `held`, `blocked`, `reversed`, `rejected`} — exhaustive, all six values map to a receipt-driven UI label:

| `status` | Creator-facing label |
|---|---|
| `processing` | Payout processing |
| `paid` | Paid *(the "Royalty earned $X" toast is copy shown alongside this state, not a distinct status value)* |
| `held` | Held for risk review |
| `blocked` | Blocked |
| `reversed` | Reversed |
| `rejected` | Rejected |

Receipts are signed by Archisynapse so Lyrica (and creators) can verify them independently.

## 7. Error Codes

| HTTP | code | Meaning | Lyrica behavior |
|---|---|---|---|
| 201 | — | Obligation accepted, receipt in body | Persist receipt, update Earnings |
| 200 | — | Duplicate idempotency key, same payload | Treat as success; receipt is identical |
| 400 | `invalid_schema` | Malformed body / bad bps sum / bad amount format | Fix and re-emit with NEW idempotency key |
| 401 | `invalid_signature` | Signature does not verify | Alert; do not retry until keys fixed |
| 403 | `unknown_key` / `tenant_mismatch` | Key not registered / key ≠ tenant | Alert; config issue |
| 409 | `processing` | Same key and payload; original request still in flight | Retry/poll with the SAME identity |
| 409 | `idempotency_conflict` | Same key, different payload | Bug on Lyrica side; alert, never retry |
| 422 | `ownership_invalid` / `stale_event` | VICS/DNA check failed / replay window | Surface to creator (blocked) / re-sign fresh |
| 503 | `retry_later` | Archisynapse unavailable | Outbox retry w/ exponential backoff, SAME idempotency key |

## 8. Durability (Lyrica side, normative)

Lyrica MUST persist every obligation to a local **outbox** table before first send (state: `pending` → `sent` → `receipted` / `rejected`). Retries use the same `event_id`, `idempotency_key`, and `correlation_id`. An Archisynapse outage therefore delays, but never loses and never duplicates, a royalty.

## 9. Non-Goals for v1

Webhook/async receipt delivery (sync response is the v1 receipt channel), multi-currency, batched events, partial reversals, and streaming micro-royalty aggregation are explicitly out of scope — designed for, not built, per progressive-integration doctrine.
