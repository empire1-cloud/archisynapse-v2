# Lyrica–Archisynapse Integration Contract

## Royalty Receipt Loop v1 · Empire-1 Ecosystem

**Status:** Draft for implementation
**Products:** Lyrica 3 (producer) → Archisynapse v2 (consumer/executor)
**Boundary:** `POST /api/v1/events` on the Archisynapse gateway
**Operating rule honored:** WE EVOLVE. NEVER DELETE. Both schemas carry `schema_version`; consumers MUST tolerate unknown fields; breaking changes require a new major version, never mutation of v1.

---

## 1. Principles

1. **Lyrica creates obligations. Archisynapse moves money.** Lyrica never writes to the ledger; Archisynapse never decides what a creative act is worth.
2. **At-least-once delivery, exactly-once effect.** Lyrica may send an event any number of times; Archisynapse guarantees at most one financial effect per `idempotency_key`.
3. **Every hop shares one `correlation_id`.** It must appear in Lyrica's outbox, the gateway log, the transaction record, the journal entry metadata, and the receipt.
4. **The receipt is the only source of truth for Lyrica's Earnings screen.** Lyrica renders creator-facing status exclusively from receipt fields, never from its own guesses.

## 2. Transport & Security

| Concern | Specification |
|---|---|
| Endpoint | `POST https://{archisynapse-gateway}/api/v1/events` |
| Auth (tenant) | `Authorization: Bearer <tenant API key>` — tenant identity resolved by SLA113-issued key |
| Signature | `X-Empire1-Signature: ed25519=<base64(sig)>` over the exact raw request body bytes |
| Key identity | `X-Empire1-Key-Id: <key id>` — public keys registered per tenant via SLA113 |
| Correlation | `X-Correlation-Id: <ULID>` — generated by Lyrica at obligation creation, immutable thereafter |
| Idempotency | `Idempotency-Key: <ULID>` — unique per obligation, stable across retries |
| Replay bound | `occurred_at` in body must be within ±5 minutes of gateway clock, else `422 stale_event` (retry with same idempotency key after clock fix is safe) |
| Content type | `application/json; charset=utf-8` |

Signature verification failures are **recorded** (a rejection row with correlation_id, key_id, reason) but create **no** financial objects.

**Validation rules:** `splits[].bps` MUST sum to exactly 10000. `amount.value` is a fixed-point string with exactly 4 decimal places (matches Archisynapse BigInt ledger units). `trigger.kind` ∈ {`play`, `remix`, `license`}. Unknown top-level fields are ignored, never rejected.

## 4. Money Math (normative)

All arithmetic in integer ten-thousandths (units = value × 10000), matching the v1 monolith ledger convention.

1. **Platform fee:** 290 bps of gross, rounded **half-up to the cent**.
   `$1.2500 gross → fee = 1.25 × 0.029 = 0.03625 → $0.04. Net = $1.21.`
2. **Splits:** apply bps to net, floor each share to the cent, then distribute leftover cents by **largest fractional remainder**; ties broken by larger bps, then lexicographic `owner_id`. Deterministic — the same event always yields the same cents.
   `Net $1.21 at 60/40 → raw 0.7260 / 0.4840 → floor 0.72 / 0.48, leftover $0.01 → remainders .006 > .004 → final $0.73 / $0.48.`
3. **Invariant:** `sum(payouts) + fee == gross`, always, enforced by a balanced-journal check before commit.

## 5. Decision Outcomes & Ledger Effects

| Decision | Receipt `status` | Ledger effect |
|---|---|---|
| Allow | `processing` → `paid` | DR `royalty_clearing` 1.25 / CR `creator_payable:{owner}` 0.73 + 0.48 / CR `platform_fee_revenue` 0.04 |
| Hold | `held` | DR `royalty_clearing` 1.25 / CR `royalty_held_liability` 1.25 (obligation recorded, no payable created, no money moves) |
| Block | `blocked` | No financial entries. Decision + reasons persisted with correlation_id |
| Release (of held) | `processing` → `paid` | Reclass: DR `royalty_held_liability` / CR payables + fee, same event_id, no new obligation |
| Reversal | `reversed` | Linked reversing entries (existing v2 reversal semantics); post-reversal trial balance delta = 0 |

**Hold release:** `POST /api/v1/events/{event_id}/release` — authorized via SLA113 policy role only; idempotent (releasing twice pays once); `409 invalid_state` if not held.
**Reversal:** Lyrica emits `royalty.obligation.reversed` with `reverses_event_id`, its own `idempotency_key`, same `correlation_id`.

## 6. Unified Receipt Schema (v1)

Returned synchronously (v1) as the response body; identical object retrievable at `GET /api/v1/receipts/{receipt_id}`.

```json
{
  "schema_version": "1.0",
  "receipt_id": "rcp_01J8ZC...",
  "status": "paid",
  "status_reasons": [],
  "event_id": "01J8ZC4K7Q2M9XN3P5R7T9V1WX",
  "correlation_id": "01J8ZC4K7Q2M9XN3P5R7T9V1AA",
  "transaction_id": "txn_5f7b2571",
  "ledger_transaction_id": "ldg_txn_8d1287",
  "amounts": {
    "currency": "USD",
    "gross": "1.2500",
    "platform_fee": "0.0400",
    "net": "1.2100"
  },
  "payouts": [
    { "owner_id": "cre_a1b2c3", "amount": "0.7300", "state": "paid" },
    { "owner_id": "cre_d4e5f6", "amount": "0.4800", "state": "paid" }
  ],
  "decision": {
    "policy": "allow",
    "risk_score": 0.12,
    "checks": ["ownership_verified", "dna_match", "vics_valid"]
  },
  "issued_at": "2026-07-20T18:00:01Z",
  "signature": { "alg": "ed25519", "key_id": "arch-rcpt-k1", "value": "base64..." }
}
```

`status` ∈ {`processing`, `paid`, `held`, `blocked`, `reversed`, `rejected`}. Lyrica's Earnings screen maps these 1:1 to creator-facing labels (Royalty earned / Payout processing / Paid / Held for risk review / Blocked / Reversed). Receipts are signed by Archisynapse so Lyrica (and creators) can verify them independently.

## 7. Error Codes

| HTTP | code | Meaning | Lyrica behavior |
|---|---|---|---|
| 201 | — | Obligation accepted, receipt in body | Persist receipt, update Earnings |
| 200 | — | Duplicate idempotency key, same payload | Treat as success; receipt is identical |
| 400 | `invalid_schema` | Malformed body / bad bps sum / bad amount format | Fix and re-emit with NEW idempotency key |
| 401 | `invalid_signature` | Signature does not verify | Alert; do not retry until keys fixed |
| 403 | `unknown_key` / `tenant_mismatch` | Key not registered / key ≠ tenant | Alert; config issue |
| 409 | `idempotency_conflict` | Same key, different payload | Bug on Lyrica side; alert, never retry |
| 422 | `ownership_invalid` / `stale_event` | VICS/DNA check failed / replay window | Surface to creator (blocked) / re-sign fresh |
| 503 | `retry_later` | Archisynapse unavailable | Outbox retry w/ exponential backoff, SAME idempotency key |

## 8. Durability (Lyrica side, normative)

Lyrica MUST persist every obligation to a local **outbox** table before first send (state: `pending` → `sent` → `receipted` / `rejected`). Retries use the same `event_id`, `idempotency_key`, and `correlation_id`. An Archisynapse outage therefore delays, but never loses and never duplicates, a royalty.

## 9. Non-Goals for v1

Webhook/async receipt delivery (sync response is the v1 receipt channel), multi-currency, batched events, partial reversals, and streaming micro-royalty aggregation are explicitly out of scope — designed for, not built, per progressive-integration doctrine.
