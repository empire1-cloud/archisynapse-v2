● Fair enough — here's the gist in a nutshell:

  - Manual scaling: set instance count 1–100 (Dashboard/CLI/API), all instances
  share the same plan.
  - Autoscaling: Professional+ workspaces only, set min/max instances plus
  CPU/memory targets (1–90%). If both metrics are on, it scales to whichever
  number is more conservative (larger).
  - Vertical vs horizontal: bump the plan (CPU/RAM) for memory-hungry or
  single-threaded workloads; add instances for stateless, request-heavy traffic.
  Often you do both — right-size the plan, then scale out.
  - Gotchas: services with a persistent disk are stuck at 1 instance; static
  sites don't scale (CDN-served); cron jobs/workflows don't use this model at
  all.
  - Billing: per-second, roughly compute-time × instance count — no extra fee
  just for scaling actions.

  If you ever do want to put Archisynapse on Render, it'd need a render.yaml

❯ # Lyrica–Archisynapse Integration Contract                                    
                                                                                
  ## Royalty Receipt Loop v1 · Empire-1 Ecosystem                               
                                                                                
  **Status:** Draft for implementation                                          
  **Products:** Lyrica 3 (producer) → Archisynapse v2 (consumer/executor)       
  **Boundary:** `POST /api/v1/events` on the Archisynapse gateway               
  **Operating rule honored:** WE EVOLVE. NEVER DELETE. Both schemas carry       
  `schema_version`; consumers MUST tolerate unknown fields; breaking changes    
  require a new major version, never mutation of v1.                            
                                                                                
  ---                                                                           
                                                                                
  ## 1. Principles                                                              
                                                                                
  1. **Lyrica creates obligations. Archisynapse moves money.** Lyrica never     
  writes to the ledger; Archisynapse never decides what a creative act is       
  worth.                                                                        
  2. **At-least-once delivery, exactly-once effect.** Lyrica may send an event  
  any number of times; Archisynapse guarantees at most one financial effect per 
  `idempotency_key`.                                                            
  3. **Every hop shares one `correlation_id`.** It must appear in Lyrica's      
  outbox, the gateway log, the transaction record, the journal entry metadata,  
  and the receipt.                                                              
  4. **The receipt is the only source of truth for Lyrica's Earnings screen.**  
  Lyrica renders creator-facing status exclusively from receipt fields, never   
  from its own guesses.                                                         
                                                                                
  ## 2. Transport & Security                                                    
                                                                                
  | Concern | Specification |                                                   
  |---|---|                                                                     
  | Endpoint | `POST https://{archisynapse-gateway}/api/v1/events` |            
  | Auth (tenant) | `Authorization: Bearer <tenant API key>` — tenant identity  
  resolved by SLA113-issued key |                                               
  | Signature | `X-Empire1-Signature: ed25519=<base64(sig)>` over the exact raw 
  request body bytes |                                                          
  | Key identity | `X-Empire1-Key-Id: <key id>` — public keys registered per    
  tenant via SLA113 |                                                           
  | Correlation | `X-Correlation-Id: <ULID>` — generated by Lyrica at           
  obligation creation, immutable thereafter |                                   
  | Idempotency | `Idempotency-Key: <ULID>` — unique per obligation, stable     
  across retries |                                                              
  | Replay bound | `occurred_at` in body must be within ±5 minutes of gateway   
  clock, else `422 stale_event` (retry with same idempotency key after clock    
  fix is safe) |                                                                
  | Content type | `application/json; charset=utf-8` |                          
                                                                                
  Signature verification failures are **recorded** (a rejection row with        
  correlation_id, key_id, reason) but create **no** financial objects.          
                                                                                
  ## 3. Royalty Event Schema (`royalty.obligation.created`, v1)                 
                                                                                
  ```json                                                                       
  {                                                                             
    "schema_version": "1.0",                                                    
    "event_id": "01J8ZC4K7Q2M9XN3P5R7T9V1WX",                                   
    "event_type": "royalty.obligation.created",                                 
    "occurred_at": "2026-07-20T18:00:00Z",                                      
    "correlation_id": "01J8ZC4K7Q2M9XN3P5R7T9V1AA",                             
    "idempotency_key": "01J8ZC4K7Q2M9XN3P5R7T9V1BB",                            
    "tenant_id": "lyrica",                                                      
    "track": {                                                                  
      "track_id": "trk_9f3a2b1c",                                               
      "dna_tag": "dna_v2_7c1e...",                                              
      "soulprint_hash": "sp_sha256_4b09...",                                    
      "vics_proof": {                                                           
        "proof_id": "vics_01H...",                                              
        "issued_at": "2026-07-01T12:00:00Z",                                    
        "chain_ref": "vics://empire1/lyrica/trk_9f3a2b1c"                       
      }                                                                         
    },                                                                          
    "creator": {                                                                
      "creator_id": "cre_a1b2c3",                                               
      "identity_ref": "sla113://identity/cre_a1b2c3"                            
    },

      { "owner_id": "cre_a1b2c3", "bps": 6000 },

  ```                                                                           
                                                                                
  **Validation rules:** `splits[].bps` MUST sum to exactly 10000.               
  `amount.value` is a fixed-point string with exactly 4 decimal places (matches 
  Archisynapse BigInt ledger units). `trigger.kind` ∈ {`play`, `remix`,         
  `license`}. Unknown top-level fields are ignored, never rejected.             
                                                                                
  ## 4. Money Math (normative)                                                  
                                                                                
  All arithmetic in integer ten-thousandths (units = value × 10000), matching   
  the v1 monolith ledger convention.                                            
                                                                                
  1. **Platform fee:** 290 bps of gross, rounded **half-up to the cent**.       
     `$1.2500 gross → fee = 1.25 × 0.029 = 0.03625 → $0.04. Net = $1.21.`       
  2. **Splits:** apply bps to net, floor each share to the cent, then           
  distribute leftover cents by **largest fractional remainder**; ties broken by 
  larger bps, then lexicographic `owner_id`. Deterministic — the same event     
  always yields the same cents.                                                 
     `Net $1.21 at 60/40 → raw 0.7260 / 0.4840 → floor 0.72 / 0.48, leftover    
  $0.01 → remainders .006 > .004 → final $0.73 / $0.48.`                        
  3. **Invariant:** `sum(payouts) + fee == gross`, always, enforced by a        
  balanced-journal check before commit.                                         
                                                                                
  ## 5. Decision Outcomes & Ledger Effects                                      
                                                                                
  | Decision | Receipt `status` | Ledger effect |                               
  |---|---|---|                                                                 
  | Allow | `processing` → `paid` | DR `royalty_clearing` 1.25 / CR             
  `creator_payable:{owner}` 0.73 + 0.48 / CR `platform_fee_revenue` 0.04 |      
  | Hold | `held` | DR `royalty_clearing` 1.25 / CR `royalty_held_liability`    
  1.25 (obligation recorded, no payable created, no money moves) |              
  | Block | `blocked` | No financial entries. Decision + reasons persisted with 
  correlation_id |                                                              
  | Release (of held) | `processing` → `paid` | Reclass: DR                     
  `royalty_held_liability` / CR payables + fee, same event_id, no new           
  obligation |                                                                  
  | Reversal | `reversed` | Linked reversing entries (existing v2 reversal      
  semantics); post-reversal trial balance delta = 0 |                           
                                                                                
  **Hold release:** `POST /api/v1/events/{event_id}/release` — authorized via   
  SLA113 policy role only; idempotent (releasing twice pays once); `409         
  invalid_state` if not held.                                                   
  **Reversal:** Lyrica emits `royalty.obligation.reversed` with                 
  `reverses_event_id`, its own `idempotency_key`, same `correlation_id`.

  retrievable at `GET /api/v1/receipts/{receipt_id}`.

  earned / Payout processing / Paid / Held for risk review / Blocked /          
  Reversed). Receipts are signed by Archisynapse so Lyrica (and creators) can   
  verify them independently.                                                    
                                                                                
  ## 7. Error Codes                                                             
                                                                                
  | HTTP | code | Meaning | Lyrica behavior |                                   
  |---|---|---|---|                                                             
  | 201 | — | Obligation accepted, receipt in body | Persist receipt, update    
  Earnings |                                                                    
  | 200 | — | Duplicate idempotency key, same payload | Treat as success;       
  receipt is identical |                                                        
  | 400 | `invalid_schema` | Malformed body / bad bps sum / bad amount format | 
  Fix and re-emit with NEW idempotency key |                                    
  | 401 | `invalid_signature` | Signature does not verify | Alert; do not retry 
  until keys fixed |                                                            
  | 403 | `unknown_key` / `tenant_mismatch` | Key not registered / key ≠ tenant 
  | Alert; config issue |                                                       
  | 409 | `idempotency_conflict` | Same key, different payload | Bug on Lyrica  
  side; alert, never retry |                                                    
  | 422 | `ownership_invalid` / `stale_event` | VICS/DNA check failed / replay  
  window | Surface to creator (blocked) / re-sign fresh |                       
  | 503 | `retry_later` | Archisynapse unavailable | Outbox retry w/            
  exponential backoff, SAME idempotency key |                                   
                                                                                
  ## 8. Durability (Lyrica side, normative)                                     
                                                                                
  Lyrica MUST persist every obligation to a local **outbox** table before first 
  send (state: `pending` → `sent` → `receipted` / `rejected`). Retries use the  
  same `event_id`, `idempotency_key`, and `correlation_id`. An Archisynapse     
  outage therefore delays, but never loses and never duplicates, a royalty.     
                                                                                
  ## 9. Non-Goals for v1                                                        
                                                                                
  Webhook/async receipt delivery (sync response is the v1 receipt channel),     
  multi-currency, batched events, partial reversals, and streaming              
  micro-royalty aggregation are explicitly out of scope — designed for, not     
  built, per progressive-integration doctrine.

  0. What's actually wrong, precisely

  The current code (services/gateway/royalty_ledger_client.py,
  royalty_orchestrator.py) has the gateway calling the ledger service's
  /accounts and /transactions endpoints directly. That's not just a style issue
  — it contradicts a boundary this codebase already states explicitly for the
  card-payment loop:

  ▎ services/gateway/orchestrator.py, line 8: "The Gateway never posts directly 
  ▎ — it queries by referenceId if needed."
  ▎ services/transaction/transaction-service-ledger-client.ts, lines 4-7: "The 
  ▎ Transaction Service NEVER writes ledger data directly... This keeps the 
  ▎ ledger as the single source of financial truth."

  I broke a rule the repo already enforces for the loop that exists. The royalty
  loop needs to follow the same shape.

  Also confirmed by re-reading the real transaction service's schema
  (transaction-service-schema.sql) and API (transaction-service-api.ts): its
  payments table is card-payment-shaped (payment_method_type NOT NULL, one
  customer_id, one payable) — it has no concept of multi-owner splits. Extending
  it, not routing around it, is the correct fix.

  1. Corrected data flow

  Lyrica (signed event)
    → Gateway: feature flag, tenant auth, ed25519 signature, schema, replay
  window
    → Gateway: decision call (fraud/ownership) — NEVER default-allow
    → Gateway → Transaction Service: POST /royalties (real transaction_id minted
  here)
    → Transaction Service → Ledger Service: POST /transactions (real
  ledger_transaction_id minted here)
    → Transaction Service returns {transaction_id, ledger_transaction_id,

    → Gateway: builds + signs receipt, persists to Postgres (not JSON files)
    → Gateway → Lyrica: receipt (sync response + GET /api/v1/receipts/{id})
    → Lyrica: outbox marks receipted, Earnings renders from receipt fields only

  The gateway's job shrinks to: authenticate, verify, decide, delegate, receipt.
  It never touches accounts or transactions on the ledger again.

  royalty_obligations(event_id);
  CREATE INDEX idx_royalty_obligations_organization_id ON
  royalty_obligations(organization_id);

  CREATE TABLE royalty_payouts (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    royalty_obligation_id UUID NOT NULL REFERENCES royalty_obligations(id),
    owner_id VARCHAR(255) NOT NULL,
    amount NUMERIC(19,4) NOT NULL CHECK (amount > 0),
    state VARCHAR(20) NOT NULL DEFAULT 'PAID'

  );

    idempotency_key VARCHAR(255) NOT NULL,
    request_hash VARCHAR(64) NOT NULL,
    receipt_id VARCHAR(255) NOT NULL REFERENCES royalty_receipts(receipt_id),
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, idempotency_key)
  );

  CREATE TABLE royalty_rejections (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    correlation_id VARCHAR(255),
    key_id VARCHAR(255),
    reason VARCHAR(100) NOT NULL,
    occurred_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
  );

  CREATE TABLE royalty_tenant_keys (
    tenant_id VARCHAR(255) NOT NULL,
    key_id VARCHAR(255) NOT NULL,
    public_key_b64 VARCHAR(255) NOT NULL,
    revoked_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, key_id)
  );

  CREATE TABLE royalty_tenant_api_keys (
    tenant_id VARCHAR(255) PRIMARY KEY,
    api_key_hash VARCHAR(255) NOT NULL,     -- argon2id, never plaintext

  subprocess+SQLite approach — CI time goes up; worth confirming that's
  acceptable before making it the only test path.
  - Migrating .runtime/*.json → Postgres is a one-way door for any state already
  written (the .runtime/royalty_* files from this session's local runs).

  value is lost — but flagging it since "WE EVOLVE, NEVER DELETE" is the house
  rule and I want that judgment call visible, not silent.
  - Argon2/hashing adds a new dependency (argon2-cffi) to a service that
  currently has none of that class — small, standard, low risk.

  7. Rollback plan

  - Every change above is additive at the service level (new tables, new
  endpoints, new gateway modules) except the deletion of
  royalty_ledger_client.py's direct-ledger-write path, which is exactly the
  thing being corrected — there is no "roll back" for that, only forward to the
  correct boundary.
  - ROYALTY_LOOP_ENABLED=false (default) means the entire loop can be disabled
  instantly without a deploy/rollback — it fails closed, not open. This is the
  actual rollback mechanism: flip one env var, not revert commits.
  - If the transaction-service extension proves wrong in review, the new
  royalty_obligations/royalty_payouts tables and royalty-service-*.ts files can
  be dropped/reverted independently of the gateway's Postgres migration —
  they're separate migrations, separate services, no cross-coupling that would
  force an all-or-nothing revert.
